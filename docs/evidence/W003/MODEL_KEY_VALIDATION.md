# Local model key validation prototype

[Architecture #3](https://github.com/igorpooh1978/GoEF/issues/3) · [Error contract #2](https://github.com/igorpooh1978/GoEF/issues/2) · [MODEL-VALID-001-S01](../../../specs/features/model/model-valid-001.feature) · [Logical model design](../../architecture/MODEL_ENGINE.md)

The prototype checks explicit logical model declarations. A required primary key cannot include a property whose resolved nullability permits NULL. The validator preserves member order and returns the first invalid declaration's numeric entity, property and key-member positions. Its portable cause is `GOEF-MODEL-0001` with phase `validate-model` and retry class `never`. Diagnostics retain no declaration names. Valid composite keys and nullable non-key properties pass. An empty key declaration leaves trackability for later model validation.

EF Core 10.0.15 rejects nullable properties in `EntityType.AddKey`. Its Fluent `HasKey` can first make a member required. GoEF's prototype checks the resolved declaration and treats an explicit nullable key member as a contradiction. Go type representation, default conventions and precedence between declaration sources remain work for the model mapping stage. The Go implementation was written independently of the pinned MIT-licensed C# source. [Key validation](https://github.com/dotnet/efcore/blob/b34c0e9d7e768aa808ded44f19e7f871bea6869f/src/EFCore/Metadata/Internal/EntityType.cs#L646-L685) · [Fluent key builder](https://github.com/dotnet/efcore/blob/b34c0e9d7e768aa808ded44f19e7f871bea6869f/src/EFCore/Metadata/Internal/InternalEntityTypeBuilder.cs#L220-L275) · [Pinned tests](https://github.com/dotnet/efcore/blob/b34c0e9d7e768aa808ded44f19e7f871bea6869f/test/EFCore.Tests/Metadata/Internal/PropertyTest.cs#L143-L178)

The first executable checks failed with a no-op validator. Additional checks reproduced a panic for a typed nil error and an invalid coordinate in the zero value. Both cases now yield a safe fallback message and no portable cause. Independent review verified the revised implementation and test controls on local revision `217f14efea2ba1f92bcb8a5347070b1d131559c5`.

On 2026-11-26, `go build -mod=readonly ./...`, `go vet -mod=readonly ./...` and `go test -mod=readonly -shuffle=on -count=1 -cover ./...` exited 0 on the Windows/amd64 workstation with Go 1.27.4. Both prototype packages showed 100% statement coverage. `go test -mod=readonly -race -shuffle=on -count=1 ./...` exited 0 using the same revision and Go version in an isolated local Linux/amd64 container. The prototype imports the standard library and its portable error package. It has no provider or driver dependency.

The prototype code is available in the local model worktree. Acceptance into the implementation branch still requires the [project license decision](https://github.com/igorpooh1978/GoEF/issues/15) and the mapping and application gates for the full model scenario. The four provider entries remain specified pending the application entry point.

## Deterministic snapshot prototype

Local revision `f1c404f87d13e1a3d48050db802bdb7245ed9a5c` adds an internal JSON snapshot experiment. The trial format validates declarations in their original order, sorts entities by exact name, preserves property and primary-key member order and uses arrays for empty lists. It rejects malformed UTF-8 before encoding, using the original numeric declaration position and a safe message. Returned bytes are independent of the input slices.

The tests first failed with direct encoding. They then verified identical bytes after entity registration order changed, different bytes after property or key order changed, stable results after the input was mutated and no bytes for invalid declarations. Independent Windows/amd64 review at Go 1.27.4 recorded exit 0 for `go build -mod=readonly ./...`, `go vet -mod=readonly ./...` and `go test -mod=readonly -shuffle=on -count=1 -cover ./...`. The two model prototype packages reached 100% statement coverage in that review.

The source pin preserves composite-key member order when constructing the key and assigns a separate physical ordinal to each column. The Go trial keeps the resolved declaration's property order and leaves physical ordinals and generated source to the later design-time scenario.
