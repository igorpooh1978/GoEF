## Behavior and upstream sources

The previous GoEF API coordinates a *sql.Tx. Go 1.27.4 gives database/sql both a begin context and automatic rollback on context cancellation. GoEF used an independent control context so its own cleanup could preserve the result. The characterization command below passes on the baseline and confirms acknowledged and unconfirmed cleanup after cancellation during native begin. Passing the caller's context into the same database/sql begin would let two owners race to roll back. [Go 1.27.4 implementation](https://github.com/golang/go/blob/go1.27.4/src/database/sql/sql.go) · [Baseline test](../../../transaction/failure_test.go)

The native pgx path uses caller-controlled begin and commit because the pgx begin context governs only the begin command. Returning a pooled transaction through pgx would give up its connection as part of native completion. GoEF uses a separately acquired pool checkout so it can remove the physical connection when commit is inconclusive. The v5.13.0 driver distinguishes an explicit PostgreSQL ROLLBACK command tag at commit through pgx.ErrTxCommitRollback. The adapter maps that acknowledgement to the portable ErrCommitRolledBack. [Pinned pgx transaction](https://github.com/jackc/pgx/blob/v5.13.0/tx.go) · [Pool checkout ownership](https://github.com/jackc/pgx/blob/v5.13.0/pgxpool/conn.go) · [PostgreSQL COMMIT](https://www.postgresql.org/docs/18/sql-commit.html) · [pgx license](https://github.com/jackc/pgx/blob/v5.13.0/LICENSE)

Pinned EF Core verifies that a participating context reads state from its enclosing transaction and treats borrowed transaction disposal separately. GoEF uses that ownership distinction with an explicit pgx coordinator, serial operation gate and caller-owned native completion. No upstream source was copied. [Pinned implementation](https://github.com/dotnet/efcore/blob/b34c0e9d7e768aa808ded44f19e7f871bea6869f/src/EFCore.Relational/Storage/RelationalTransaction.cs) · [Pinned specification tests](https://github.com/dotnet/efcore/blob/b34c0e9d7e768aa808ded44f19e7f871bea6869f/test/EFCore.Relational.Specification.Tests/TransactionTestBase.cs)

## Execution

The disposable server used PostgreSQL 18.7, server_version_num 180007, with SCRAM authentication on localhost and a synthetic marker checked before writing. Client configuration used pgx v5.13.0, Exec query mode and one worker connection per scenario. An independent connection observed backend identity, locks and rows. Go 1.27.4 windows/amd64 and Python 3.14.4 executed the local runner. It stopped the server and removed its temporary data on completion.

| Scenario | Observed result |
| --- | --- |
| TX-PG-NATIVE-001-S01 | Queue timeout issued no BEGIN. A deadline observed by the driver entry tracer while GoEF held a checkout returned the standard cause and no handle. Fresh transactions confirmed each requested isolation level with read-only enabled and rolled back. |
| TX-PG-NATIVE-001-S02 | The transaction backend waited on a held advisory lock. Lifetime cancellation preserved its standard cause and consumed the checkout. The observer found no committed row and the caller pool remained usable. |
| TX-PG-NATIVE-001-S03 | A deferred trigger placed the backend in an advisory lock wait during an already dispatched COMMIT. The canceled driver call produced one commit attempt, a typed unknown outcome and a replacement backend. After the original backend terminated, the independent observer found no row. The API kept the outcome unknown pending explicit reconciliation. |
| TX-PG-NATIVE-001-S04 | An enlisted participant saw the application's pending row. Another batch was rewound, including its staged receipt. A canceled scan preserved its cause and owner detachment preserved the native checkout. The owner rolled back and the pool remained usable. |
| TX-PG-NATIVE-001-S05 | A failed statement left the transaction aborted. PostgreSQL explicitly confirmed rollback when COMMIT was attempted. GoEF returned ErrCommitRolledBack with StateRolledBack, redacted the pgx sentinel and reused the same idle backend. The independent observer saw no row and a fresh transaction committed. |

Commands and exits

- Baseline go test ./transaction -run TestCancelDuringNativeBeginPreservesCleanupOutcome -v exited 0, including both cleanup paths.
- Implementation go test -shuffle=on -count=1 -coverprofile <core-profile> ./transaction ./goeferr exited 0. It covers typed nil inputs and late cancellation when native BEGIN already succeeded, with both acknowledged and failed cleanup.
- From the repository root, python -B test/conformance/lab/postgres_native_tx.py --bin-dir <postgres-18.7-bin> --count 3 --coverprofile <live-profile> exited 0. All five scenarios passed three times.
- go vet ./transaction ./goeferr and go build ./... exited 0 in the core module. go build ./..., go vet ./... and go test -shuffle=on -count=1 ./... exited 0 in the PostgreSQL module. Test runs outside the private fixture intentionally skip its live cases.
- go test -race -shuffle=on -count=1 failed before running on this Windows host. The default environment disabled cgo. Retrying core with CGO_ENABLED=1 found no GCC executable. An independently provisioned supported race environment remains pending.
- PgBouncer modes, the application's pool budget and cross-engine acceptance for the combined change remain pending. They are outside this direct PostgreSQL fixture.

The PostgreSQL package covered 72 of 73 (98.63%). The provider's new transaction implementation covered 47 of 47 statements and the core native bridge covered 36 of 36.
