# SaveChanges recovery inside a transaction

[Issue #2](https://github.com/igorpooh1978/GoEF/issues/2) · [Transaction guide](../../user/TRANSACTIONS.md) · [Ownership scenarios](../../../specs/features/transactions/tx-own-001.feature) · [Savepoint scenarios](../../../specs/features/transactions/tx-savepoint-001.feature)

An explicitly ordered save batch uses the existing physical transaction and one private savepoint under the same operation gate. A recoverable failure rewinds the batch and leaves earlier writes pending. Staged assignments stay unapplied on error. After a successful save they remain provisional until the caller accepts a confirmed commit that includes the saved batch. Automatic graph detection, model-driven SQL generation and full change tracking retain separate W011 acceptance. [Pinned EF Core batch executor](https://github.com/dotnet/efcore/blob/b34c0e9d7e768aa808ded44f19e7f871bea6869f/src/EFCore.Relational/Update/Internal/BatchExecutor.cs#L56-L147) · [Pinned EF Core state manager](https://github.com/dotnet/efcore/blob/b34c0e9d7e768aa808ded44f19e7f871bea6869f/src/EFCore/ChangeTracking/Internal/StateManager.cs#L1353-L1389) · [Pinned recovery test](https://github.com/dotnet/efcore/blob/b34c0e9d7e768aa808ded44f19e7f871bea6869f/test/EFCore.Relational.Specification.Tests/TransactionTestBase.cs#L1229-L1265)

The engine fixture exercises three scenarios through the public API, including a generated parent key and a partially written graph with a duplicate child, a caller-owned transaction with a successful earlier write, and an unsupported configuration that rejects a save before the callback or any writes. It uses transaction-preserving DML, a read-only SQL Server `XACT_ABORT` check, and a fresh physical observer. For the negative SQL Server configuration the fixture also enables `XACT_ABORT` and proves the owner can commit its earlier write. [Executable fixture](../../../test/conformance/driverlab/save_changes_transaction_test.go) · [SQL Server XACT_ABORT](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-xact-abort-transact-sql?view=sql-server-ver16) · [SQL Server XACT_STATE](https://learn.microsoft.com/en-us/sql/t-sql/functions/xact-state-transact-sql?view=sql-server-ver16)

Recovery is limited to commands that preserve the enclosing transaction and a configuration that supports savepoints. PostgreSQL documents rollback to a retained point. SQLite's `ROLLBACK` conflict strategy can end the transaction. InnoDB can roll back the whole transaction on deadlock, and the pinned MySQL driver can close its connection on in-flight cancellation. The controlled failure tests exercise unconfirmed recovery separately from the statement-level constraint errors used in the real-engine fixture. [PostgreSQL](https://www.postgresql.org/docs/19/sql-rollback-to.html) · [SQLite](https://www.sqlite.org/lang_conflict.html) · [InnoDB](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html) · [Pinned MySQL driver](https://github.com/go-sql-driver/mysql/blob/v1.10.0/README.md#contextcontext-support)
