# SaveChanges recovery inside a transaction

[Issue #2](https://github.com/igorpooh1978/GoEF/issues/2) · [Transaction guide](../../user/TRANSACTIONS.md) · [Ownership scenarios](../../../specs/features/transactions/tx-own-001.feature) · [Savepoint scenarios](../../../specs/features/transactions/tx-savepoint-001.feature)

An explicitly ordered save batch uses the existing physical transaction and one private savepoint under the same operation gate. A recoverable failure rewinds the batch and leaves earlier writes pending. Staged assignments stay unapplied on error. After a successful save they remain provisional until the caller accepts a confirmed commit that includes the saved batch. Automatic graph detection, model-driven SQL generation and full change tracking retain separate W011 acceptance. The engine fixture exercises three scenarios through the public API, including a generated parent key and a partially written graph with a duplicate child, a caller-owned transaction with a successful earlier write, and an unsupported configuration that rejects a save before the callback or any writes. It uses transaction-preserving DML, a read-only SQL Server `XACT_ABORT` check, and a fresh physical observer. For the negative SQL Server configuration the fixture also enables `XACT_ABORT` and proves the owner can commit its earlier write.
