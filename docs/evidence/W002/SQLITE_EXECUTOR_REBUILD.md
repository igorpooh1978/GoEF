# Recover an interrupted SQLite migration through the GoEF executor

[Issue #13](https://github.com/igorpooh1978/GoEF/issues/13) · [Product scenario MIG-SQLITE-001-S03](../../../specs/features/migrations/mig-sqlite-001.feature) · [Executor](../../../migration/sqlite/apply.go) · [Worker](../../../test/conformance/driverlab/sqlite_executor_rebuild_test.go) · [Compatibility runner](../../../test/conformance/lab/sqlite_compat.py)

## Behavior

The executor pins one physical connection and begins an immediate write transaction before reading the database identity and ordered history. It requires the reviewed source and target checks around the supplied operation. It verifies the reserved history table before running operations and checks the table again before adding the new entry. The insert must affect exactly one row and the reread must match the full expected lineage. The final foreign-key check precedes the atomic commit. Rollback and settings restoration use a bounded cleanup context. An unconfirmed commit discards the connection and returns the portable outcome error.

The synthetic migration copies an explicit writable projection, preserves a generated value and the AUTOINCREMENT watermark, restores the index and trigger, and writes a new row. Its postcondition verifies the rebuilt state and the still-unmodified history. A faulting child exits at code 69 inside that check. The runner requires this exit and the product worker marker for the selected engine and journal mode. It allocates each file in an owned disposable directory.

The next worker verifies the old schema, bytes, generated value, sequence, index, trigger, relationship and exact history. It exercises a mismatched database identity and artifact digest, an unexpected dependent view, a suppressed history write, a callback failure, an orphan foreign key and a competing writer. The writer wait returns the migration lock error. Late operation failures roll back and preserve the old data and history. The worker checks that the single-connection pool enforces foreign keys after rollback and after commit. After one successful apply, an exact history and target match end in a no-op and a divergent target returns the recovery error. A different read-only process verifies the committed schema, values, constraints and exact two-entry history without using the writer's connection.

## Research and boundaries

The implementation follows the vendor's generalized create, copy, drop and rename procedure and acquires the write lock before reading durable preconditions. Both pinned driver sources expose extended result codes for the writer lock classification. The pinned EF Core command executor distinguishes transactional commands from transaction-suppressed commands. Its SQLite generator uses a replacement-table projection and temporarily changes foreign-key enforcement outside a transaction. Its tests also reject a rebuild without model information. GoEF uses caller-authored checks and groups the entire reviewed rebuild with history. The implementation and synthetic fixture were written independently.
