# Isolated provider conformance lab

[Issue #16](https://github.com/igorpooh1978/GoEF/issues/16) designs the lab for [W002 #13](https://github.com/igorpooh1978/GoEF/issues/13). The four candidates have published artifacts. The [executable smoke lab](../../test/conformance/lab/README.md) uses isolated native clients for baseline engine checks. GoEF runtime conformance is **0/4**. The [artifact and host observations](../evidence/W002/TEST_LAB_DESIGN.md) distinguish available builds from selected dependencies and observed engine identities.

## Runner and resource ownership

Use a fresh native Linux/amd64 GitHub-hosted VM for each server job. Run the Go test process, the engine and any fault controller on a private job network with no published database port. Download approved artifacts before isolating the workers. Give the controller access only to the current job's resources. Keep container management and the daemon socket outside the test process. SQLite runs inside its own job process and on its own disposable local filesystem. Start a separate job for GoLINQ Objects with neither credentials nor an engine. Run expression/compiler fixtures independently. Match any EF comparison to the same engine, seed and settings in a separately seeded target. The [LINQ comparison protocol](../../test/conformance/linq/README.md) defines how to compare rows, multiplicity and order.

The provisioner generates a random run token, records the job/attempt and resource IDs, and hands the worker only its private endpoint, target name, role and expected token. Each scenario or outline example gets a fresh target and seed. A test requiring a process or engine restart has exclusive use of its instance and volume for the full test. Cross-session tests share only that scenario's target. A separate instance or file hosts isolation controls. Record allocations before setup, including partial creations.

Build connection settings inside the job from an ephemeral manifest. Never import a workstation DSN, cloud database URL or default local socket. Match exact endpoint, database or canonical file under the private temporary directory, TLS peer identity where applicable, and a provisioner-owned marker before handing out a writer. Grant application roles read-only access to that marker. A mismatched marker, target or settings aborts setup before fixture changes. Keep credentials in job-local secrets or permission-restricted files. Upload allowlisted structured fields. Exclude raw server messages, DSNs, connection options containing secrets, environment dumps, traces of values and database files.

## Synthetic seed and clock

Seed revision `orders-v1` starts with tenants 1 and 2 and the rows below. The primary key is the integer ID. Declare a unique key on (tenant, ID) and have the child foreign key refer to that pair. Define a uniqueness constraint on the operation marker. A separate migration variant declares generated values, dependencies, a trigger and an index before taking its baseline snapshot. Bind all values. A fresh observer reads back the seed in ID order before the first operation.

Keep case/accent and NULL ordering expectations per provider and observed collation. Seed replacement, nullable and scaled decimal variants explicitly when the scenario requests them. Record a hash of canonical ordered values and schema revision for each variant.

Use fixed UTC values for data and a controllable clock for retry backoff in Go-only tests. Use the monotonic clock for real server deadlines and elapsed time. Set the PostgreSQL and MySQL session time zones to UTC and confirm them on checkout. Store explicit UTC values in the SQL Server and SQLite fixtures and read them back with the selected type. Capture runner UTC and start/finish times as evidence metadata. Choose initial wall-time budgets of 180 s for readiness, 5 s per connection attempt, 15 s per operation, 60 s per scenario cleanup and 30 min per job. Reserve time for cleanup outside the canceled request. Report observed phase and elapsed time when a budget expires. A readiness timeout blocks the cell.

## Scenario execution

Expand the existing tags and Examples in the [Gherkin inventory](../../specs/README.md) into named cases keyed by scenario ID, provider, version and settings. Check every selected step has a binding and at least one assertion against the real result. Treat missing bindings, skipped rows, duplicate cases and failed setup as visible gaps. These examples define the first runs. Keep the full [transaction](../../test/conformance/transactions/README.md) and [migration](../architecture/MIGRATION_ENGINE.md) acceptance matrices for the implementing waves.

For PostgreSQL, include an interrupted concurrent index build and inspect validity and definition. For SQL Server, include a failed save with a doomed transaction and check owner rollback plus persisted rows. Use the provider's manifest for additional settings and negative capabilities. Before promoting any additional provider-specific case to traceability, the feature owner assigns or binds its Gherkin ID. For durable backfill, stop after batch one has committed and before acknowledging its checkpoint, then check which primary keys changed and whether a second transformation would duplicate any effect. Trace intent, dispatch, acknowledgement and final history separately.

Use named barriers between processes, with an independent watchdog. For server lock waits correlate the waiting session and the held resource. For SQLite prove file sharing and busy-handler entry, or record the specific unobservable phase as blocked. Never infer engine entry from elapsed sleep. A fault controller can gate and disconnect only the allocated test connection. A real engine response supplies native error evidence. Injected transport or cleanup errors carry their own origin in the report.

## Implementation sequence and acceptance

1. Freeze the W001 provider-facing contract, driver mode, supported settings, runner, license/EULA decision and exact artifacts. Verify the manifest digest and platform before startup and the runtime build and Go module graph on startup. Validate the seed and marker, permission checks, parallel-target isolation and post-teardown inventory first. Assign the runner implementation and remaining scenario bindings under [#13](https://github.com/igorpooh1978/GoEF/issues/13).
2. Implement lifecycle and named scenario discovery before binding application behavior. Bring up each provider independently. Add rejection controls for a wrong target marker, missing engine, wrong version, missing step and cleanup failure. Demonstrate the gate rejects each. Bind the simplest positive, native-negative, cancellation and migration-restart rows first. Record behavioral RED or characterization before the relevant implementation, then GREEN on the integrated SHA. Keep setup failures outside behavioral RED.
3. Create five distinct required suite results for Objects and the four real providers, plus separate compiler/expression checks. Suggested GitHub job labels are `objects`, `postgres`, `sqlite`, `sqlserver` and `mysql`; encode the settings profile and actual build in each result. Use independent matrix legs with fail-fast off. A proposed hosted label is `ubuntu-22.04` x64. Record actual runner image version, CPU architecture, available memory and disk, Docker version and Go 1.27.4. Verify SQL Server's supported host, edition terms and resources before acceptance. A cancelled or missing job leaves the aggregate incomplete. [Hosted runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) · [SQL Server installation guidance](https://learn.microsoft.com/en-us/sql/linux/install-upgrade/setup?view=sql-server-ver16)
4. For each row record integrated SHA, scenario, named Go test, fixture revision, provider and driver, settings, phase, command/exit, attempt, elapsed time, expected/observed states, redacted native code, cleanup and artifact hash. Preserve the Gherkin-to-test links in [traceability](../../specs/traceability.json). Keep PASS, FAIL, BLOCKED, NOT RUN and reviewed unsupported outcomes visible with a reason. Link to upstream license/pin in the [source lock](../upstream/lock.json) for differential fixtures. An unavailable EF/MySQL baseline blocks that comparison separately.
5. Publish independent coverage numerators/denominators per provider and module with explicit owned package sets. Record each provider's statement coverage and the number of executed mandatory behavior cells over all required cells, including settings profiles. Apply the [coverage gates](COVERAGE.md), including 95% per owned production module and provider. Preserve separate unit, race and engine profiles and the integration suite's exact commands. Compare instrumented builds before merging any compatible profiles. The reviewer verifies both failure semantics and persisted state against the integrated SHA.
6. Always close readers, transactions, workers, pools and fault controls, then check locks and settle process exits. Collect coverage and redacted evidence before teardown. Delete only provisioner-owned resources by recorded IDs after rechecking the owner token, including volumes and networks or the verified fixture directory. Retrying cleanup uses the same ownership checks, a fresh bounded context and at most two retries. Confirm the pre-run inventory is restored. A survivor fails cleanup, records its ID and quarantines the runner. A hosted VM's eventual destruction does not establish that the harness cleaned up. Re-run a failed scenario on a newly allocated target and retain both attempt results.

Independent acceptance replays one selected scenario and deliberate rejection per provider and checks the complete matrix on the same candidate SHA. The design slice ends with the protocol and [read-only feasibility record](../evidence/W002/TEST_LAB_DESIGN.md). W002 runtime acceptance requires the executed evidence above.
