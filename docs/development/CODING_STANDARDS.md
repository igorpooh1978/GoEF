# Go coding standards

GoEF targets Go 1.27.4. Check the actual toolchain and module directives before using version-specific features. Run compiler probes for generic method chaining and nongeneric SPI boundaries before freezing signatures. Keep methods with their own type parameters off interfaces. Arbitrary Go function values are executable callbacks for local LINQ; database queries use inspectable typed expressions or an approved generated AST plan.

- Format changed Go files with `gofmt` and use the configured import/lint rules. Use short purposeful package names, idiomatic Go names, explicit dependencies and narrow interfaces owned by consumers. Keep driver types inside provider modules and portable behavior in the core. Keep public APIs typed and useful at their zero value where the contract supports it.
- Pass `context.Context` explicitly as the first argument to cancellable I/O. Document concurrency guarantees, goroutine ownership, termination, row/stream cleanup and transaction affinity. Check terminal row errors. Avoid holding locks across I/O. Bound retries and concurrency.
- Parameterize SQL values. Validate or dialect-quote identifiers at the provider boundary. Preserve null, precision, collation and ordering semantics and keep provider-specific capabilities visible. Treat raw SQL and destructive migrations as explicit APIs with documented constraints.
- Return regular operational failures as registered typed errors. Preserve causes only where allowed by the public contract and use `errors.Is` or `errors.As` for decisions. Translate driver errors at the boundary, redact diagnostic values and keep cancellation and ambiguous commit distinct. Avoid stale generated files, placeholders, ignored errors and hidden fallback.
- Write English Godoc for public semantics. Start comments with the symbol name and explain ownership, cancellation, concurrency, errors and caveats callers can observe. Put non-obvious internal invariants beside the code they constrain.
- Keep dependencies, Go directives, generator versions and released migrations unchanged unless an explicitly approved issue authorizes the specific change. Update schema/templates and regenerate with the pinned tool. Preserve existing issued migration contents and use a new forward migration for changes.
- Run `go vet ./...` and `go test -race -shuffle=on ./...` for each touched module on supported platforms. Run configured lint, vulnerability and generation checks, plus affected real-engine contract tests. Use standard-library tests, deterministic fault synchronization, isolated fixtures and measured benchmarks as described in [Testing](TESTING.md) and [Coverage](COVERAGE.md).

Use the [issue workflow](ISSUE_WORKFLOW.md), [architecture](../architecture/OVERVIEW.md), [documentation policy](DOCUMENTATION_POLICY.md) and [Skills policy](SKILLS.md). Optional local Go guidance is useful when consistent with these contracts. A guide aimed at application servers does not set an ORM API or mandate a dependency.
